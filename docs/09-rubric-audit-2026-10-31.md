## 必须优先修复的项目

### P0：补出一个真实多模态闭环

目标：上传一张通知截图或 PDF 后，完成“解析 → 证据段落/页码 → 任务 → Reviewer”。

最低可交付版本：

1. 浏览器端限制大小和 MIME，显示隐私提示。
2. API 接收图片/PDF，服务端提取文本；没有视觉模型时提供明确的 demo OCR 适配器。
3. 返回 `sourceId/page/locator/excerpt`，写入当前会话证据。
4. 计划任务必须引用该证据，Reviewer 检查缺失字段和个人信息。
5. 演示中用一张固定截图完成闭环，并显示解析耗时和失败回退。

这项直接关系多模态 5 分和实用性/创新证据。

### P0：让服务端 Planner 的结果进入页面主流程

目前 `App.tsx` 调用 `/api/plan` 后主要更新 `modelPlanLabel`；页面任务队列仍来自 `initialTasks` 和本地 `scheduleTasks`。

需要让 `/api/plan` 返回的结构化任务经过校验后：

- 进入任务队列；
- 绑定证据 ID；
- 进入 Reviewer；
- 显示真实 `mode/model/fallbackReason`；
- 在演示记录中显示 traceId、耗时和失败原因。

否则评委可能认为后端模型只是展示标签。

### P1：补 MCP/工具调用证据

至少实现两个只读工具并在 UI 展示调用链：

- `check_opening_hours`
- `check_materials` 或 `check_calendar_conflict`

工具参数使用 JSON Schema 校验，返回 `tool_call → tool_result`，失败时显示真实原因并保留重试/人工路径。可以先做项目内 MCP server 或 MCP 风格函数调用，但要在演示中明确协议和输入输出。

### P1：补结构化 schema 和混合检索

- 为 Planner、Evidence、Task、ToolResult 增加 schema 校验。
- RAG 增加 BM25/关键词 + 可插拔 embedding 接口，至少在日志中显示阈值、Top-k 和未命中原因。
- 保留当前 demo fallback，避免评审现场因模型服务不可用而无法演示。

### P1：修正能力文案

在多模态尚未完成前，上传按钮应明确写成“上传文本通知（图片/PDF 解析开发中）”，或者先完成 P0 后再保留现有入口。这样不会被评委认为功能宣传与实际不符。
