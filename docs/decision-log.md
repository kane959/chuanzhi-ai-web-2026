# 决策记录

## 2026-10-27 · 选题定为 CampusFlow

- **决定**：第一条演示闭环聚焦“新生在截止日前完成多项校园事务”。
- **依据**：官方 AI WEB 赛道把 AI 技术深度列为 35%，创新性列为 25%；附件问卷中 84.38% 的回答者访问 AI 网站是为了解决具体问题。
- **可证伪点**：如果真实访谈无法确认新生愿意把通知交给系统，改成“仅解析与核对，不代办”的工具型产品。

## 2026-10-28 · 产品与参赛学校解耦

- **决定**：CampusFlow 使用通用校园场景和自建合成资料，不把广州航海学院写成产品用户、数据来源或官方背书。
- **原因**：学校信息只服务于报名材料；作品需要能公开演示和迁移到其他高校，避免未经授权使用校内资料或制造学校关联。
- **影响**：README、产品简报和团队资料明确区分“参赛信息”和“产品事实”；真实学校知识包只能在获得授权后接入。

## 2026-10-27 · 先做本地演示模式

- **决定**：没有 API Key 时也能完整播放 Planner → Retriever → 工具校验 → 人工确认的流程，并在 UI 明确标注演示模式。
- **原因**：评委需要稳定复现；前端不能保存共享密钥，也不能把静态结果伪装成实时模型输出。
- **后续**：真实模型通过服务端适配器接入，同一份 `Evidence`、`Task`、`AgentEvent` 契约保持不变。

## 2026-10-27 · 检索先用本地 BM25/SQLite

- **决定**：省赛纵向切片先用可追溯的本地资料包和 BM25，向量数据库只作为可插拔优化。
- **原因**：知识包规模小、证据定位比向量召回更重要；本地方案便于离线演示和固定评测。
- **验收**：每个计划任务必须带来源 ID、定位、更新时间和相关度；不足证据时返回 `insufficient_evidence`。

## 2026-10-27 · 外部写入采用预览与撤销

- **决定**：日历写入、导出或提交动作都先展示预览，等待用户确认。
- **原因**：校园场景含个人信息和不可逆操作；这也是 Reviewer 能力和社会价值评分的可见证据。
